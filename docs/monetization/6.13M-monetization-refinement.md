## 1. Purpose

The **6.13M** workstream refines monetization **without merging** subscription plans and paid advertising into one commerce model.

Goals:

- Keep **Plans** (subscription entitlements) and **Advertising** (campaign commerce) as **separate products** with separate lifecycles.
- Reduce owner-facing semantic confusion (especially **VIP plan** vs **VIP banner**).
- Harden campaign lifecycle, pricing admin, and production plan billing incrementally.
- Preserve documented invariants while improving safety and operability.

Foundational product rules (unchanged intent):

- **Plans and Advertising are separate products.**
- **VIP Plan ≠ HOME_VIP_BANNER** (subscription tier vs purchasable ad placement).
- **Advertising does not affect organic business ranking** (plan tier is not used in organic sort comparators).
- **Promotion content ≠ Promoted Promotion** (owner `Promotion` entity vs `PROMOTED_PROMOTION` monetization product).
- **Mobile and Consumer Web** consume the same catalog-api monetization/ad-serving backend (placement codes and serve APIs shared).

## 3. Core Invariants

1. **VIP Plan does not automatically create HOME_VIP_BANNER.**
2. **HOME_VIP_BANNER can be purchased independently** from VIP Plan (separate product/order/campaign).
3. **Paid plan tier does not alter organic business ranking** (`compareBusinessCatalogRank` / tier rank comparators).
4. **Promotion (content) and Promoted Promotion (ad product) are separate.**
5. **Plan downgrade does not delete business content** (entitlement sync / publish limits; not content wipe).
6. **Business Profile does not serve competitor ads** — no business-profile ad placement in `SERVING_PLACEMENT_CODES` (serving scoped to home/category placements).
7. **`AD_SERVED` ≠ `AD_IMPRESSION`** — serve selection vs client-qualified impression.
8. **`SEARCH_TOP` remains inactive** for serving unless a future stage explicitly enables it.
9. **`MAP_FEATURED` remains inactive** for serving unless a future stage explicitly enables it.
10. **Mobile and Web use the unified ad-serving backend** (shared placement codes and catalog-api serve paths).
11. **Historical Orders and Payments remain readable** (no destructive migration policy in 6.13M).
12. **Existing advertising campaigns must remain valid** through refactors (additive schema preferred).

If a future stage changes an invariant, **do not delete** the old rule — document the change, stage, rationale, and tests.

## 6. 6.13M.2 — Campaign Lifecycle / Moderation Period Safety

| Field | Value |
|---|---|
| **Status** | Implemented |
| **Production behavior** | YES — campaign date/status resolution |
| **Schema** | NONE |
| **API** | NONE |

### Previous issue

For **creative-required** campaigns (`VIP_BANNER`), pre-approval scheduling could set:

`endAt = paidAt + purchased duration`

so **moderation time appeared to consume** the paid delivery window; availability could treat **`PENDING_MODERATION`** as **COMPLETED** when a short legacy `endAt` passed.

### New behavior

For creative-required campaigns awaiting moderation:

- **`PENDING_MODERATION`** uses a **placeholder `endAt`** (`moderationPendingPlaceholderEnd`, +10 years from anchor) — delivery duration starts **after** creative approval, not during moderation.
- On approval, **`resolveOnCreativeApproved`** sets real window:
  - no `desiredStartAt` → starts at approval;
  - future `desiredStartAt` → starts at `desiredStartAt`;
  - past `desiredStartAt` → starts at approval;
  - full purchased duration preserved from effective start.

Also:

- **`PENDING_MODERATION`** does not serve as active delivery.
- Expiration / availability logic no longer maps **`PENDING_MODERATION` → COMPLETED** solely from expired placeholder/legacy `endAt`.

After payment:

### Long provisional `endAt` (+10y)

Prevents paid VIP inventory from being resold while creative awaits moderation.

**Tradeoff:**

- Prevents overbooking;
- Unresolved moderation can hold capacity a long time;
- **No moderation TTL/SLA** in product code.

**Operational risk**, not treated as an immediate backend logic bug in 6.13M.2A.

### Lifecycle capacity release (documented behavior)

- **REJECTED** — releases capacity (campaign not delivering)
- **CANCELLED** — releases capacity
- **APPROVED** — transitions to real delivery window (placeholder end replaced)

## 9. 6.13M.4 — Production Plan Billing Foundation

| Field | Value |
|---|---|
| **Status** | **Implemented** (working tree; **checkpoint commit pending**; migration applied on **local `qalago_dev`** as of 6.13M.4A) |
| **Production behavior** | YES — when deployed with migration |
| **Schema** | YES — additive |
| **API** | YES — owner purchase + admin plan payments |

### Previous state (before 6.13M.4)

- No **PENDING** plan purchase lifecycle for production.
- Paid activation via **mock checkout** and **admin tier override** only.
- **`PlanPayment`** created as **COMPLETED** at immediate activation.
- Owner could not create a production pending purchase awaiting admin confirmation.

### Architecture decision

**Extend `PlanPayment` (Option A).** Do **not** route plan billing through advertising **`Order` / `Payment` / `AdCampaign`**.

**Why not reuse ad commerce:**

- `OrderItem` is ad-product-oriented; ad payment confirm **provisions campaigns**.
- Coupling plan activation to ad order flow increases blast radius and breaks isolation invariants.

### Schema / migration

**Migration:** `20261003103000_plan_payment_billing_6_13m4` (additive)

- **`PlanPaymentStatus`:** added **`PENDING`**, **`CANCELLED`**; kept **`COMPLETED`**, **`FAILED`**
- **`PlanPayment`:** nullable **`paidAt`**; **`provider`** (default `MANUAL`); **`providerReference`**; **`idempotencyKey`** (unique); **`updatedAt`**; **`periodDays`** snapshot
- Prisma default **`status = COMPLETED`** retained for historical compatibility; **new production purchases set `PENDING` explicitly**

### Billing lifecycle (implemented)

1. Owner **`POST /api/v1/businesses/:businessId/plan/purchases`** (`tier`, optional `idempotencyKey`)
2. Server snapshots **`amountKzt`** + **`periodDays`** from **`PLAN_CATALOG`**
3. Creates **`PlanPayment`** **`PENDING`**, **`paidAt = null`** — **does not** change `Business.planTier` / `planExpiresAt`
4. Admin **`POST /admin/plans/payments/:id/confirm`** (step-up, `PAYMENT_CONFIRM`)
5. Transaction: conditional **`PENDING → COMPLETED`**, **`applyTierEntitlement`**, set payment **`expiresAt`**, audit, **`PLAN_ACTIVATED`** **once**
6. Optional **`POST …/cancel`** → **`CANCELLED`**

**Mock checkout** (`POST …/plan/mock-checkout`, dev flag): still immediate **`COMPLETED`** + activation — explicit status at create.

**Confirm does not create a second `PlanPayment`** — uses `applyTierEntitlement` only.

### Same-tier renewal (product correction)

If current tier equals purchased tier and **`planExpiresAt > activationTime`**:

- `base = planExpiresAt`
- `newExpiresAt = base + periodDays` (from payment snapshot)

Else: `newExpiresAt = activationTime + periodDays`

### Upgrade

Higher tier purchase while not same-tier renewal: **`activationTime + periodDays`** — **no proration** in 6.13M.4.

### Downgrade protection

Active higher paid tier + purchase of lower paid tier → **rejected** (`PLAN_DOWNGRADE_NOT_ALLOWED`). No scheduled downgrade.

### Owner / Admin UI

- **business-web** `/plan` — production CTA creates pending purchase when mock checkout disabled
- **admin-web** `/plans/payments` — list / confirm / cancel (separate from `/monetization/payments`)

### API summary

| Method | Path | Audience | Permission |
|---|---|---|---|
| POST | `/businesses/:id/plan/purchases` | Owner | owner (`assertOwner`) |
| GET | `/businesses/:id/plan/payments` | Owner | `PAYMENTS_VIEW` |
